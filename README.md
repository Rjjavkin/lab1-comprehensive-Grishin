# Итоговый аналитический отчет (Лабораторная работа №1)

## 1. Резюме 
В рамках лабораторной работы спроектирован процесс разработки нового микросервиса «Расчет корзины и скидок» для системы лояльности. Целью работы являлось создание надежной инженерной инфраструктуры, минимизирующей риск попадания дефектов в финансовую логику расчетов. 

В ходе работы выполнен сравнительный анализ СУБД, настроена модель ветвления с защитой основной ветки разработки, внедрен автоматический контроль качества кода (CI/CD с линтером `flake8`), проведено обратное проектирование legacy-алгоритма с построением UML-диаграммы деятельности и разработан регламент проведения Code Review.

## 2. Сравнительный анализ технологий

### 2.1. Матрица принятия решений

| Критерий выбора | Вес | PostgreSQL (балл 1–5) | PostgreSQL (взвеш.) | MongoDB (балл 1–5) | MongoDB (взвеш.) |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **1. Поддержка ACID-транзакций** (надежность списания/начисления баллов) | 0.35 | 5 | 1.75 | 3 | 1.05 |
| **2. Строгая целостность и консистентность данных** (связи транзакций) | 0.25 | 5 | 1.25 | 3 | 0.75 |
| **3. Производительность чтения и агрегаций** (аналитика истории баллов) | 0.20 | 4 | 0.80 | 4 | 0.80 |
| **4. Гибкость схемы данных** (разные форматы правил промокодов) | 0.10 | 4 | 0.40 | 5 | 0.50 |
| **5. Зрелость экосистемы и стоимость владения** | 0.10 | 5 | 0.50 | 4 | 0.40 |
| **ИТОГО** | **1.00** | — | **4.70** | — | **3.50** |

### 2.2. Расчет и обоснование выбора
Расчет взвешенной оценки выполнен по формуле:
\[\text{Оценка} = \sum (\text{Вес}_i \times \text{Балл}_i)\]

* **PostgreSQL:** \((0.35 \times 5) + (0.25 \times 5) + (0.20 \times 4) + (0.10 \times 4) + (0.10 \times 5) = 1.75 + 1.25 + 0.80 + 0.40 + 0.50 = \mathbf{4.70}\)
* **MongoDB:** \((0.35 \times 3) + (0.25 \times 3) + (0.20 \times 4) + (0.10 \times 5) + (0.10 \times 4) = 1.05 + 0.75 + 0.80 + 0.50 + 0.40 = \mathbf{3.50}\)

**Обоснование выбора:** Победителем выбрана реляционная СУБД **PostgreSQL** (4.70 балла против 3.50 у MongoDB). Для микросервиса, оперирующего финансовыми транзакциями и бонусными баллами, ключевым требованием является строгая согласованность данных и полная поддержка ACID-транзакций (максимальный вес `0.35`). Наличие типа данных `JSONB` в PostgreSQL также позволяет гибко хранить произвольные параметры промокодов, нивелируя главное преимущество документоориентированной MongoDB.

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма
По результатам анализа legacy-функции `calculate_cart_total` построена UML-диаграмма деятельности, отражающая последовательность применения базовой скидки, перебор промокодов в цикле, учет уровня лояльности и ограничение максимальной скидки порогом в 30%.

<img width="378" height="785" alt="image" src="https://github.com/user-attachments/assets/c1f7392d-1b75-415c-883e-4aa458f68650" />

**Список выявленных «запахов кода» (Code Smells) в legacy-фрагменте:**
1. **Магические числа (Magic Numbers):** в коде напрямую используются числовые литералы `15000`, `0.85`, `500`, `0.90`, `0.97`, `0.93`, `0.70` без вынесения в именованные константы, что затрудняет понимание бизнес-правил.
2. **Отсутствие валидации входных данных:** функция не проверяет отрицательные значения `cart_sum`, некорректные типы списка `promos` и неизвестные значения `tier`.
3. **Использование `float` для денежных расчетов:** операции с плавающей точкой (`* 0.85`, `* 0.97`) могут приводить к ошибкам округления; для финансов рекомендуется использовать тип `Decimal`.
4. **Жесткая связность бизнес-логики (Hardcoded Logic):** названия промокодов (`"SUMMER"`, `"VIP"`) и коэффициенты уровней зашиты в условные операторы `if/elif`, что нарушает принцип открытости/закрытости (OCP) при добавлении новых акций.
5. **Отсутствие аннотаций типов (Type Hints) и документации (Docstring):** сигнатура функции не описывает ожидаемые типы аргументов и возвращаемого значения.

### 5.2. План code-review
Для безопасного рефакторинга модуля `src/discount.py` подготовлен план проведения инспекции кода.
* **Открытый Pull Request с планом ревью и UML:** [ЗДЕСЬ ВСТАВИТЬ ССЫЛКУ НА ОТКРЫТЫЙ PR из feature/review-plan в develop]
* **Ключевые измеримые критерии:**
  * Полное отсутствие магических чисел (вынос в константы или конфигурацию).
  * Наличие валидации входных параметров (защита от отрицательной суммы корзины).
  * Покрытие модульными тестами (Unit Tests) не менее 80%, включая граничные случаи.
  * Нулевое количество предупреждений линтера `flake8`.
* **Механизм эскалации:** при возникновении разногласий в комментариях PR обсуждение ограничено 4 рабочими часами, после чего назначается 15-минутный созвон. Споры по бизнес-логике скидок эскалируются Product Owner'у, архитектурные вопросы решает Tech Lead.

## 6. Заключение
Внедрение многоуровневого контроля качества (защита ветки `develop`, обязательные Pull Request, автоматический запуск линтера `flake8` в CI/CD и формализованный процесс Code Review) позволяет выявлять синтаксические, стилистические и логические ошибки до попадания кода в основную ветку. Предварительное обратное проектирование legacy-кода с помощью UML-диаграммы помогло зафиксировать текущую бизнес-логику и выявить критические уязвимости (магические числа, отсутствие валидации и риск ошибок округления) еще до начала этапа разработки.
